## Timestamp semantics fixed from source and Apple documentation

- Native record `at_s` is `CACurrentMediaTime()` sampled when the numeric event is recorded. For `metal_update` that occurs after retaining the supplied drawable and reading native getters, before invoking the existing GPUI callback. It is not an exact delegate-entry timestamp. Cross-thread callback delivery order is not GPU execution order.
- `metal_update.deadline_s` is `CAMetalDisplayLink.Update.targetTimestamp`: the time by which the drawable's presentation method is expected to have been called. GPU rendering may continue afterward according to preferred latency. It is **not a GPU completion deadline**. [Apple targetTimestamp](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink/update/targettimestamp)
- `target_presentation_s` is the distinct estimated display target, used for animation timing. It is not guaranteed actual display time. [Apple targetPresentationTimestamp](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink/update/targetpresentationtimestamp)
- `submit_begin` occurs only after drawable acquisition/slot consumption and renderer mode selection. `submit_end` is after the rendering/presentation/commit path returns. These enclose CPU-side elapsed time, including waits; neither is an exact commit, driver scheduling, or drawable-present timestamp.
- The normal `command_buffer.present_drawable` call registers deferred presentation through command scheduling; actual `drawable.present()` happens later. Thus `submit_end` relative to the CPU deadline cannot establish that the drawable's presentation method itself met or missed it. The transaction path has a different sequence and is likewise unstamped. [Apple command-buffer present](https://developer.apple.com/documentation/metal/mtlcommandbuffer/present(_:))
- Completed-handler `GPUStartTime/GPUEndTime` are command-buffer GPU host-time endpoints; valid after completion and0 when unavailable. Their elapsed interval is not CPU duration or percentage of peak GPU utilization. GPU-end after the CPU deadline is not by itself a missed display; compare the separate target and actual outcome. [Apple GPUStartTime](https://developer.apple.com/documentation/metal/mtlcommandbuffer/gpustarttime)
- Positive drawable `presentedTime` is actual host-time display information;0 means no positive presentation reported. Record callback arrival separately from that timestamp. A missing callback remains missing/censored, never converted to0. [Apple presentedTime](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime)
- `frame_decision.used_drawable` means the renderer slot was consumed. Rendering can still have failed or returned without successful submission. `paused` is the computed end-of-callback pause decision, not an `isPaused` getter. Wake events are requests, not frames, CPU wakeups, or measured executions.
- History markers are render-captured logical coordinates reported during prepaint, before measurement can update a following viewport. They are scene-associated logical geometry, not raster displacement. The marker is last-known outside History, so acquisition must stay on that surface.

## Joins and missing data

Build joins over the complete captured file before applying any analysis window, so callbacks after a selected interval still classify its submissions. Updates and decisions join by(window,drawable); submissions/end/completions/present callbacks join by(window,call), validating drawable agreement. If a key has multiple candidates, flag the ambiguity and retain all candidates rather than silently selecting the latest. Unmatched/capture-boundary records and missing markers remain explicit. Do not assume global numeric `at_s` order across asynchronous callbacks; preserve sequence and timestamps.

Acquisition completeness separately requires the actual sequence-bearing record count to match the footer, with unique ordered contiguous sequences1 throughN, a header, one arm, one final duration-complete footer, and zero recorder drops/marker overflow. A retained zero-drop footer cannot conceal a missing interior record or duplicate sequence. A failed integrity check leaves a partial diagnostic report and cannot be treated as an intact capture. This is independent of drawable outcomes: a fully recorded zero/missing/error outcome is retained. A null/nonfinite-serialized presented timestamp is explicitly unavailable rather than zero, missing or positive; null logical coordinates remain unknown poses.

For each update retain assigned deadline/target/rate/latency, callback recording time, actual slot/pause decision, observed submission count and zero/positive/missing outcomes. Slot-consumed with no recorded submission and an update with no decision remain unclassified mechanisms, not invented dropped/success flags.

For each submission retain new/reused previous-submission scene flag, actual scene revision/marker, submit begin/end, valid GPU host interval/status, and positive/zero/missing presentation callback. Compute signed milliseconds for update-record→submit begin, submit begin→end, CPU-path end−CPU deadline, GPU start/end−CPU deadline, GPU end−estimated display target, actual positive display−estimated target, and prepaint marker→actual display. Label the CPU deadline values **relative timing**, not proved present-call misses/met. No commit/enqueue/scheduling callback/driver-kernel stamps are available.

Group exact duplicate estimated presentation targets by(window,target), over all captured updates. Primary groups use exact serialized timestamps; do not choose a tolerance after observing data. Count updates/drawables/observed submissions/scene revisions/pose values/outcomes per group, including updates with no submission. Compare record order and actual displays descriptively. A repeated assigned target alone does not prove a bug, last-wins policy or compositor cause.

Report a contingency of positive/zero/missing outcomes against GPU-end before/after the estimated target and CPU-path-return before/after its deadline, retaining unavailable GPU/end/update joins. An early-completed zero drawable is an observed association, not proof of compositor suppression; commit/present-call scheduling and other consumers remain unobserved.
